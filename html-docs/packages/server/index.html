Documentation

What it is, and why it exists

Every HeySnap computer runs the same machine server. It is the single HTTP and WebSocket surface the rest of the product talks to — the filesystem on disk, the file previewer, the agent threads and their streaming runs, the user’s dedicated browser, and the installed tools and skills, all reached through one process on one port. The UI never sees more than this one surface.

The package is deliberately host-shape agnostic inside cloud environments. On a cloud VM, the code runs as a Node process behind an outbound tunnel to the HeySnap gateway. The protocols on the wire are identical across provisioned machines — same routes, same WebSocket frames, same /status — so the selected machine can change without the UI knowing the difference.

Bundling everything into one process pays for itself in restart discipline. The server counts active sessions across every subsystem and reports a single safeToRestart flag; cloud supervisors gate updates on it before restarting the host artifact. The runtime entry points stay small: src/index.ts is the CLI and src/runtime.ts exposes startServer.

uniform

Same protocols, local or remote

The UI uses the same HTTP routes and WebSocket frames whether the server lives across a process boundary or across the internet. Selecting a different machine swaps the address, not the contract.

composed

One HTTP server, six subsystems

Path-prefix dispatch routes HTTP; a small upgrade router multiplexes WebSocket paths onto a single http.Server. Each subsystem owns its protocol, its watchers, and its session counter.

restartable

Sessions, status, safeToRestart

/status reports per-subsystem active session counts. Cloud supervisors wait for total === 0 before applying a release, so live work is never interrupted mid-stream.

The big picture — six things in one process

The package splits into six subsystems wired together by two small files at the root. src/runtime.ts is the factory — it builds the services, dispatches HTTP routes by path prefix, and threads every WebSocket upgrade through a tiny router. src/index.ts is the CLI wrapper that reads env vars, starts the server, and optionally opens the outbound cloud tunnel.

Each subsystem owns its own protocol and its own session counter. The filesystem owns chokidar watches and a WebSocket session per client; the agent owns SSE envelopes and a buffered run manager; browser control owns a WebSocket relay to the user’s Chrome; capabilities owns long-running install operations. They don’t share state — only the upgrade router and the /status surface.

A WebSocket relay plus an HTTP request queue. The agent asks this server to drive the browser; the browser, running on the user’s machine, dials in and executes.

A small catalog of tools (Codex, gh, Vercel, Supabase, image-gen) and bundled skills. Install, connect, refresh status — including long-running interactive flows.

Optional. When the cloud env vars are set, dials out to the HeySnap gateway and multiplexes inbound HTTP and WebSocket requests back into localhost. Auto-reconnects.

Anatomy of two requests

Two transports carry almost everything in this server: WebSockets for stateful sessions like the filesystem and the previewer, and SSE for the one-direction event stream of an agent run. Both traces below are end-to-end, from the client’s first frame to the cleanup on disconnect.

A filesystem subscribe

The client opens a WebSocket to /filesystem and wants a live view of one directory.

  1. 1

    Upgrade routed to /filesystem

    runtime → upgrade router

    runtime.ts registered the route at boot via attachFilesystemWebSocketServer(server, ...). When the upgrade arrives, the shared upgrade router matches the pathname and hands the socket to the filesystem WebSocketServer.

    runtime.ts · websocket/upgrade-router.ts · filesystem/websocket.ts
  2. 2

    hello + auto-subscribe

    server → client

    A new FilesystemSocketSession sends a hello frame carrying the root name, server time, and any restored viewState (the remembered currentPath and open files from earlier connections on this process). Without waiting for a client message, the session calls subscribe() on either the remembered path or ?path= from the URL.

    filesystem/websocket.ts · FilesystemSocketSession.start
  3. 3

    Sandbox & list

    paths · service

    resolveClientPath() rejects anything that escapes the configured root — .. segments, absolute paths, or symlinks that resolve outside. service.listDirectory() then reads the directory, filters hidden entries unless asked, and sorts directories-first.

    filesystem/paths.ts · filesystem/service.ts
  4. 4

    snapshot frame

    server → client

    One JSON frame: { type: "snapshot", reason: "subscribe", listing }. The client now has the full directory contents and can render. The session records this as the new activePath.

    filesystem/types.ts · FilesystemServerMessage
  5. 5

    Watcher attaches

    chokidar

    replaceWatcher() tears down any previous watcher and starts a fresh chokidar watch on the active directory with depth: 0 and ignoreInitial: true — one socket, one watcher.

    filesystem/websocket.ts · replaceWatcher
  6. 6

    Changes debounce, then push

    watcher → client

    Any event from the watcher schedules a debounced publish (100 ms by default). The session re-reads the directory and sends another snapshot, this time with reason "watch". No polling, no diff — the full listing is small and the client replaces it.

    filesystem/websocket.ts · scheduleSnapshot
  7. 7

    Mutations: ack then a fresh snapshot

    client → server → client

    createFolder, upload, rename, trash all follow the same shape: service call, ack with the result, then a re-listed snapshot with reason "mutation". The watcher would have fired too, but the explicit snapshot keeps the response tied to the request id.

    filesystem/websocket.ts · handleRawMessage

An agent run

The client posts a new run and wants to stream every event the harness produces.

  1. 1

    POST /agent/runs with a JSON body

    client → server

    Body carries path (required), content, optional threadId, optional clientRunId, optional uiContext. parseStartRunInput() validates; bad input becomes a 400 with an AgentError code.

    agent/http.ts · agent/validation.ts
  2. 2

    runManager.startRun()

    idempotent on clientRunId

    Creates an AgentRunRecord with status "starting" and an empty envelope buffer. If the same clientRunId arrives twice, the second call returns the existing record — safe to retry. The harness’s sendMessage() is called and yields an async iterable of events.

    agent/run-manager.ts · AgentRunManager.startRun
  3. 3

    SSE headers, then : connected

    server → client

    streamRun() writes a 200 with content-type: text/event-stream, cache-control: no-cache, and x-accel-buffering: no. The first payload is a comment line so proxies don’t hold the stream closed.

    agent/http.ts · streamRun
  4. 4

    Subscribe with replay offset

    run manager → response

    runManager.subscribe(run, after, cb) first flushes every already-buffered envelope past after to the callback — zero on a fresh run, possibly many on a reconnect — then attaches the callback for live envelopes.

    agent/run-manager.ts · subscribe
  5. 5

    run_start envelope

    id: 1

    The first envelope tells the client the run is live: { id: 1, type: "run_start", data: { runId, threadId, status } }. Written to the response as id: 1\ndata: {…}\n\n.

    agent/run-manager.ts · envelope shapes
  6. 6

    Harness events become envelopes

    async iterable → SSE

    Each event yielded by the harness — turn boundaries, message deltas, tool calls, thinking blocks, proposed plans — is wrapped as { id: N, type: "event", data: event }, appended to the run’s buffer, and broadcast to every subscriber.

    agent/run-manager.ts · consumeRun
  7. 7

    run_end closes the stream

    last envelope

    When the harness iterator returns, the manager emits run_end (or error), flips the record status to "completed" / "failed", unsubscribes the listener, and closes the response. The run record sticks around for 10 minutes in case a client reconnects.

    agent/run-manager.ts · envelope TTL
  8. 8

    Reconnect via Last-Event-ID

    GET /agent/runs/:runId/events

    A dropped client calls back with Last-Event-ID: N (or ?after=N). The same streamRun() path runs — the buffered envelopes after N are flushed first, then live envelopes attach if the run is still going. Same code, same envelope ids, no special replay protocol.

    agent/http.ts · /agent/runs/:runId/events

The filesystem subsystem

Five files give the server a complete, sandboxed filesystem: a typed protocol, a path guard, a service layer, a WebSocket session manager, and an HTTP download handler. Nothing outside this directory reads or writes the disk — all paths flow through paths.ts first.

The root is configured via ANK1015_FILESYSTEM_ROOT (defaulting to ~/Desktop). Every client-supplied path is root-relative: no leading slash, no .. segments, no backslashes, no null bytes. Absolute paths, symlinks that resolve outside the root, and special device entries are all silently dropped or rejected before any operation runs.

filesystem/types.ts

The protocol shapes

Discriminated unions for both directions of the WebSocket JSON protocol, plus the core data types used everywhere.

Client → server: subscribe, refresh, setOpenFiles, createFolder, upload, rename, trash, ping. Every message carries a requestId so responses can be correlated.

Server → client: hello (root info + viewState), snapshot (full listing with a reason tag), ack (mutation result), error, pong.

FilesystemEntry FilesystemListing FilesystemViewState SnapshotReason
filesystem/paths.ts

Sandboxing & path resolution

resolveClientPath(root, raw) is the single entry point for untrusted paths. It normalises the input, joins it under the root with path.resolve, then calls ensureWithinRoot which checks the resulting relative path doesn’t start with .. and isn’t absolute. If either condition fails the call throws PATH_OUTSIDE_ROOT before any I/O happens.

validateEntryName rejects ., .., forward and back slashes, and null bytes, keeping mutation targets to simple single-component names. Symlinks are re-validated at their resolved realpath — a symlink pointing out of the root is silently filtered from listings, not an error.

resolveClientPath toClientPath ensureWithinRoot validateEntryName
filesystem/service.ts

Core filesystem operations

FilesystemService owns all I/O. Each method resolves its path through paths.ts, performs one operation, and returns a typed result. No watchers, no WebSocket awareness here.

listDirectory — reads the dir with readdir({ withFileTypes: true }), filters hidden entries and unsafe symlinks, sorts directories first then alpha, and returns a FilesystemListing with root-relative paths.
createFolder — auto-generates “untitled folder” / “untitled folder 2” etc. if no name is given.
uploadFiles — validates each relativePath, checks for duplicates, creates directories shallowest-first, writes files with flag: "wx" (no overwrite), and preserves mtime from the client’s updatedAt.
trashEntries — delegates to the trash package (OS recycle bin); tests swap in removeEntriesForTest which calls rm -rf.

listDirectory createFolder uploadFiles renameEntry trashEntries
filesystem/websocket.ts

Session lifecycle & watching

attachFilesystemWebSocketServer registers /filesystem in the upgrade router and spawns a FilesystemSocketSession per connection. One mutable viewState object is shared across all sessions in the process and carries currentPath and openFilePaths — restored to new connections when the path still exists on disk.

Each session keeps one chokidar watcher on the active directory (depth: 0, ignoreInitial: true) that re-lists and pushes a fresh snapshot on change, debounced at 100 ms. Open-file paths are tracked too, but only as a list stored on viewState via setOpenFiles — the server doesn't watch them itself; the client picks up content changes from the same directory snapshot stream. The watcher is replaced on every subscribe and closed cleanly on disconnect.

FilesystemSocketSession viewState one watcher 100ms debounce
filesystem/download.ts

HTTP download — file or ZIP

GET /filesystem/download?path=…. Every path is resolved and sandboxed before any file is opened. The response shape depends on what was asked:

Single file — streamed directly with createReadStream().pipe(response) and a content-length header.
Single directory — recursed and packed into name.zip.
Multiple paths — all packed into download.zip.

The ZIP encoder is hand-rolled: no external library. It writes local file headers, data, and the central directory record with CRC-32 and DOS date/time fields, building the whole buffer in memory before responding.

stream single file hand-rolled ZIP CORS headers

Path safety

Every path — in WebSocket messages, in GET /filesystem/download, in upload relativePath fields — is normalised and checked against the root before any syscall. The root itself is determined at startup from ANK1015_FILESYSTEM_ROOT (default ~/Desktop) and never changes for the life of the process. Symlinks are validated at their resolved realpath, so a link pointing outside the root is treated as if it doesn’t exist.

The agent subsystem

The agent subsystem is the largest in the server. It covers everything from the vocabulary of messages and events, through the buffering layer that turns an async iterable into a replay-safe SSE stream, to the HTTP surface, and down to the Codex subprocess that actually drives the model. A harness interface sits in the middle: the run manager and HTTP layer only know about IAgentHarness; the Codex implementation lives behind it, as does a mock for tests.

The vocabulary — threads, messages, activities, plans

Everything the agent system can represent is defined in agent/types.ts. Reading it first makes the rest of the subsystem legible.

Content

AgentContent — what messages carry

A read-only array of content blocks. Three kinds: TextContent (plain string), ImageContent (base64 + mimeType), and FileContent (base64 + filename + mimeType). All three accept an optional metadata bag. This type is reused for user messages, assistant responses, tool results, and file attachments.

TextContent ImageContent FileContent
Messages

Four message roles

UserMessage — id, timestamp, path, content. The path records where in the filesystem the user was when they sent it.

AssistantMessage — id, timestamp, duration, model, provider, stopReason, usage (with token counts and cost), optional error, and an AssistantContent array of response / thinking / toolCall blocks.

ToolResultMessage — ties back to a tool call via toolCallId; carries isError and an optional typed details field.

CustomMessage — arbitrary JSON with an optional tag; used for harness-internal bookkeeping that shouldn’t affect the transcript.

UserMessage AssistantMessage ToolResultMessage CustomMessage

AgentThread & AgentThreadSummary

A summary carries id, title, startPath, lastPath, createdAt, updatedAt, messageCount, and an optional isStreaming flag. Summaries are what GET /agent/threads returns.

A full thread extends the summary with messages[], activities[], and optional proposedPlans[]. Threads are grouped by startPath in AgentThreadGroup[] so the UI can render a folder-scoped history view.

Live work visible in the UI

IAgentHarness

The harness contract

The interface every harness implements. Required: setup(), retrieveThreads(), getThread(), sendMessage() — returns AsyncIterable<AgentRunEvent>. Optional: editThreadUserMessage(), cancelRun(), steerRun().

Making the three advanced methods optional means a minimal harness only needs four methods to be valid. The run manager and HTTP layer guard before calling optionals and surface a typed error when the harness doesn’t support them.

setup sendMessage → AsyncIterable editThreadUserMessage? cancelRun? · steerRun?

The run manager — envelopes, SSE, replay

agent/run-manager.ts sits between the harness and the HTTP layer. It consumes the async iterable, wraps every event in a numbered envelope, buffers the buffer, and broadcasts to subscribers. Clients can attach, detach, and re-attach at any time.

AgentSseEnvelope the unit of storage & broadcast

A discriminated union of four shapes, all carrying an auto-incrementing id:

run_start
{ id: 1, type: "run_start",
  data: { runId, threadId } }
event
{ id: N, type: "event",
  data: { runId, threadId, event } }
run_end
{ id: N, type: "run_end",
  data: { runId, threadId } }
error
{ id: N, type: "error",
  data: { code, message } }

These are stored in record.envelopes[] forever (until the 10-minute TTL prune) so any subscriber that arrives late can replay from any offset.

startRun() idempotent on clientRunId

Creates an AgentRunRecord with status "starting", adds it to three maps keyed by internalId, runId (set after the first harness event arrives), and clientRunId (optional, caller-supplied). If a record with the same clientRunId already exists, the existing record is returned unchanged — so a client that retries a POST gets the same run, not a second one.

consumeRun() runs fire-and-forget (void async) alongside the synchronous return, so the caller can subscribe immediately.

subscribe() replay + live

subscribe(record, afterEnvelopeId, cb) first iterates record.envelopes and fires the callback for every envelope with id > afterEnvelopeId synchronously. Then, if the run is still active, it adds the callback to record.subscribers for live delivery. Returns an { unsubscribe } handle.

On a fresh connection afterEnvelopeId is 0 (all envelopes). On a reconnect it is the Last-Event-ID the browser sent — the standard SSE resume mechanism, no custom protocol needed.

getActiveRunForThread() smart replay offset

When GET /agent/threads/:id fetches a thread from the harness, the run manager checks whether a live run exists for that thread. If one does, it returns an AgentActiveRun that includes a replayAfterEventId — computed by comparing the buffered envelopes against the thread snapshot already returned by the harness.

Events that are already represented in the snapshot ( message.completed whose text the snapshot already contains, fully-accumulated content.deltas, completed activities) are skipped. The client only replays genuinely new events, so it doesn’t re-render content the thread already has.

10-minute TTL pruneCompletedRuns()

Called at the start of every public method. Completed or failed runs older than 10 minutes are removed from all three maps. The envelope buffer is not persisted; a server restart means all run state is gone. Clients that reconnect after a restart see a 404 on /agent/runs/:runId/events and must treat the run as finished.

The Codex harness

Four files under agent/harnesses/codex/ implement IAgentHarness against a real codex app-server subprocess.

harnesses/codex/app-server-client.ts

JSON-RPC over stdio

CodexStdioAppServerClient spawns codex app-server with stdio: ["pipe","pipe","pipe"] and reads stdout line-by-line via readline. Every outgoing call is a newline-delimited JSON-RPC request; every incoming line is parsed as a response, error, server request, or notification.

A pendingRequests map (keyed by auto-incrementing id) holds resolve/reject callbacks. On process exit, all pending requests are rejected with CODEX_APP_SERVER_EXITED. The last 20 stderr chunks are buffered and appended to the error message so crash context survives.

Codex sometimes sends server requests (e.g., item/commandExecution/requestApproval). The client auto-accepts these, emits the request and resolution as notifications, and replies { decision: "accept" } — the harness uses approval_policy = "never" in config so this path is only a safety net.

The gateway token is injected here: resolveCodexAppServerEnv() reads ANK1015_MACHINE_TOKEN_FILE, reads the token from that path, and sets ANK1015_CODEX_GATEWAY_TOKEN in the child process environment before spawning.

JSON-RPC over stdio readline stderr buffer (last 20) gateway token injection
harnesses/codex/config.ts

The Snap persona & Azure config

ensureCodexUserConfig() runs once at server startup. It only writes anything when the cloud env vars (CLOUD_SERVER_PUBLIC_URL + ANK1015_MACHINE_TOKEN_FILE) are both set — local development keeps its own codex config untouched.

When active, it writes ~/.codex/config.toml (chmod 0600) with: model_provider = "azure", model = "gpt-5.5", approval_policy = "never", sandbox_mode = "danger-full-access", web_search = "disabled", all plugin/app flags disabled, and a [model_providers.azure.env_http_headers] block that maps "api-key" to the ANK1015_CODEX_GATEWAY_TOKEN env var name — so Codex reads the gateway token from its own environment and injects it as an HTTP header on every LLM call.

CODEX_USER_INSTRUCTIONS is the full Snap system prompt (warm, direct, engineering-capable, non-developer audience, filesystem hygiene rules, etc.) embedded in the config as the instructions field.

harnesses/codex/codex-agent-harness.ts

The harness implementation

CodexAgentHarness implements IAgentHarness. All method calls go through this.client.request(method, params) or this.client.subscribe(listener). The subprocess is lazy-started on the first request.

Browser control

Every HeySnap computer has a dedicated Chrome window on the user’s machine. The agent running on the server needs to drive that browser — take screenshots, evaluate JavaScript, navigate tabs — but it can’t reach it directly because the user’s machine is not accessible from the server. Browser control solves this with a relay pattern: the Chrome extension dials out to the server over WebSocket; the agent sends commands in over HTTP; the server brokers the exchange.

Everything lives in one file: src/browser-control/service.ts. It contains the WebSocket attachment logic, the HTTP request handler, the broker, and all the protocol validation. The surface the server exposes is two endpoints: ws /browser-control for the Chrome extension, and POST /browser-control/requests for the agent.

Connection & hello

How Chrome connects

The extension upgrades to ws /browser-control. The server reads two required headers: x-heysnap-user-id and x-heysnap-access-session-id; missing either closes the socket immediately with code 1008.

After connecting, Chrome sends a { type: "hello", protocolVersion, clientId, capabilities[] } frame. The broker records clientId, capabilities, and stamps lastSeenAt. The client is not considered “ready” until hello is received — requests targeting an unready client return CHROME_NOT_CONNECTED.

Multiple connections per userId are allowed. Requests are routed to the one with the most recent lastSeenAt. When a client disconnects, all of its pending requests are immediately rejected.

hello frame isReady gate lastSeenAt routing

Attachments

Sending files to the browser

The agent can pass files from the server filesystem into a browser request by listing them in attachments[]. Each has an id, a root-relative path, and optional name and mimeType.

At request time the server resolves and validates each path (sandboxed to the filesystem root, must be a file, max 50 MB per file, 100 MB total). Only metadata is sent to Chrome initially: { id, name, mimeType, size }. Chrome then requests chunks on demand via { type: "attachment.read", attachmentId, offset, length } messages; the server reads the file and responds with attachment.chunk frames up to 512 KB each. The file is re-stat'd on each chunk to detect mid-request changes.

max 10 attachments 50 MB per file · 100 MB total 512 KB chunks on-demand pull by Chrome
Outputs

Receiving files from the browser

tab.screenshot always produces a server-side file. tab.evaluate can also declare outputs[] — paths the browser will write back to the server (e.g., a file the agent triggered a download for).

Each output is resolved to a temp path (target.heysnap-{uuid}.tmp) before the request is sent. Chrome streams chunks back via { type: "output.write", outputId, offset, dataBase64, done }; the server appends each chunk to the open temp file at the expected offset. When done: true arrives, the server closes the file and atomically renames the temp path to the final target. If the request fails or times out, all temp files are cleaned up.

max 10 outputs 100 MB per output temp path → atomic rename sequential offset validation
Limits & timeouts

Default request timeout: 30s. Maximum: 5 minutes. On timeout the broker sends { type: "cancel", requestId, reason } to Chrome before resolving with BROWSER_CONTROL_TIMEOUT. HTTP client disconnect triggers the same cancel path via AbortSignal. Attachments: max 10, 50 MB per file, 100 MB total, 512 KB chunks. Outputs: max 10, 100 MB per file, 512 KB chunks. A GET /browser-control/status endpoint returns connection state, clientId, capabilities, and lastSeenAt.

Capabilities — tools and skills

The capabilities subsystem is the server's package manager for the agent. It tracks two kinds of things: tools — CLI binaries the agent shells out to (codex, gh, vercel, supabase, image-gen) — and skills, which are folders of instruction and helper scripts copied into the Codex skills directory so the harness can pick them up. Everything is described by one hardcoded catalog, persisted to a single state.json, and surfaced through one HTTP namespace.

The catalog is not extensible at runtime. New tools and skills ship as code changes in this package. What is dynamic is the install / connect lifecycle: tools can be installed via npm or adopted from the host PATH; OAuth-style tools open an interactive PTY back to the UI; bundled skills are copied into a catalog directory and then symlinked into ~/.codex/skills when they should be active.

7a · The catalog

defaultCapabilitiesCatalog in capabilities/catalog.ts is the single source of truth. It carries a version string (2026.05.09.2) that gets stamped into the state file so older state can be migrated; an array of AgentToolDefinitions; and an array of AgentSkillDefinitions loaded at module load time from the packages/server/skills/ directory on disk.

Tool: codex

The agent harness binary

required: true, installed via npm from @openai/codex at a pinned version (default 0.128.0, overridable through ANK1015_CODEX_VERSION). Adopted automatically on startup if missing. The resolved binary path is cached as codexBin in state so the agent harness factory can find it without re-resolving PATH.

Tool: github

gh CLI — existing strategy

Adopted from the host PATH (installStrategy: existing). Has a full connect flow: gh auth login over an interactive PTY, with logic in startInteractiveConnectTool that auto-presses Enter when it sees the "Authenticate Git with your GitHub credentials?" prompt — the UI doesn't need to round-trip that confirmation.

Tool: vercel

Vercel CLI — npm + interactive login

Installed via npm (vercel@53.2.0), connected through vercel login --no-color in an interactive PTY. Disconnect is non-interactive (vercel logout --non-interactive) and sets CI=1 to suppress prompts.

Tool: supabase

Supabase CLI — existing + login

Adopted from PATH, connected via supabase login --no-browser in a PTY. Status check is supabase projects list — if it errors with "not logged in" or similar, the connection state becomes disconnected; anything else maps to error.

Tool: image-gen

Bundled image generator

required: true, installed from the npm package heysnap-image-gen at version 0.1.1. No connect flow — purely a local binary the agent invokes through the image-gen skill.

Skills

Seven bundled skill packages

Loaded from packages/server/skills/ at module load time: chrome, docx, image-gen, pdf, pptx, web, xlsx. Each directory has a skill.json manifest with id, label, version, description, and an optional activeByDefault flag.

Two tool fields tie tools to skills indirectly. attachedSkillIds on a tool declaration means "activate these skills when the tool is connected, deactivate them when it disconnects." None of the shipping tools currently use it, but the wiring in enforceLinkedSkills() is what would flip the linked skills on or off after a successful connectTool or disconnectTool call.

7b · Paths & state file

resolveCapabilityPaths() in capabilities/paths.ts picks the filesystem layout based on whether the server thinks it's running on a cloud VM. The detection is purely environment-based: if either ANK1015_COMPUTER_ID or ANK1015_MACHINE_TOKEN_FILE is set, paths default to /opt/ank1015/; otherwise they default under ~/.ank1015/. Every individual path can be overridden by its own env var.

On startup, initialize() tries the chosen paths, and if mkdir fails with EACCES/EPERM and no path was explicitly overridden, falls back to the user-writable layout. This is what keeps local development usable without root: a cloud-style layout can fail at /opt/ank1015, so it silently retries under $HOME/.ank1015.

The split between skillsCatalogDir and activeSkillsDir is important. The catalog directory holds the canonical copy of every installed skill; the active directory is what Codex actually reads. Activating a skill creates a symlink from activeSkillsDir/{id} to skillsCatalogDir/{id}; deactivating removes the symlink. The catalog entry stays put either way, so toggling is cheap.

state.json shape

Written atomically (temp file + rename). Keys: catalogVersion for migration sentinel, codexBin for the cached Codex path, tools (record keyed by tool id with installedVersion, installState, connectionState, lastError, updatedAt), skills (same shape but with active instead of connectionState), and a top-level updatedAt.

7c · The service lifecycle

AgentCapabilitiesService.initialize() runs four phases in order, each idempotent so a second call — or a recovery from a partial first call — is safe.

1

ensureDirectories & loadState

→ all five capability paths

All five directories are mkdir -p'd in parallel. The state file is read; if missing or malformed, an empty {} is assumed. State for every catalog tool and skill is materialised, merging any previously persisted fields with sensible defaults: installState: "not_installed", connectionState = "unsupported" if no status command else "unknown".

2

installBundledSkills

→ skillsCatalogDir/{id}

For each catalog skill where state's installedVersion doesn't match the manifest version, the source folder (minus the skill.json manifest) is copied into a temp directory, then atomically renamed into place. Active state is preserved across reinstalls; activeByDefault: true forces it on first install.

3

adoptTools

→ commandExists + installTool if required

For each catalog tool: probe with access(command, X_OK) first, then fall back to command -v. Required tools that aren't present (codex, image-gen) are installed inline. Optional tools that aren't present are simply marked not_installed. The Codex binary path gets resolved and cached into state.codexBin.

4

enforceLinkedSkills

→ activeSkillsDir/{id} symlinks

Walks every tool with attachedSkillIds, looks at its current connection state, and flips the linked skills' active flag accordingly — writing the catalog copy if missing, then symlinking or removing the link in activeSkillsDir. Called again after every successful connect, disconnect, install, or status refresh.

Installing a tool. installTool() first checks for an external helper at /opt/ank1015/agent-capabilities-helper: if present and executable, it shells out (via sudo on Unix) with the operation name and target id, then reloads state from disk. This is the cloud-image hook for privileged installs. Otherwise it runs the npm install itself: npm install --prefix {toolsRoot}/installed/{id} with {package}@{desiredVersion}, then symlinks node_modules/.bin/{binary} into toolsBinDir. The link uses a small retry loop — if a competing process already created the link pointing at the same source, that's a success.

Reading versions. readToolVersion() runs the tool's versionCommand with a 20s timeout, takes the first non-empty line of stdout+stderr, and stores it. Tools that always print their version banner first work cleanly; gh and supabase use "ami" ("any matching installation") as their desiredVersion because their version strings aren't compared against a target.

Connection probes. readConnectionState() runs the status command (also 20s); exit 0 means connected; any other exit gets its combined output lowercased and scanned for a fixed list of "not logged in"-style substrings ("not authenticated", "no existing credentials", "supply an access token", "starting login flow", …). A match means disconnected; everything else means error.

Interactive connect. Tools with connect.interactive: "tty" go through startInteractiveConnectTool, which uses @homebridge/node-pty-prebuilt-multiarch to spawn the binary inside a real pseudo-terminal (100×30, xterm-256color). Output bytes flow back to the operation manager as progress messages; input is written from the UI through the operation manager's writeInput(). The PTY also handles two quiet integrations:

DSR auto-reply

Cursor-position queries

If the child writes ESC[6n (Device Status Report — "where is the cursor?"), respondToTerminalQueries writes back ESC[1;1R. Some CLIs block on this if no terminal is attached; the server fakes a row-1, col-1 cursor so the prompt continues.

VT escape node-pty
gh "Press Enter" auto-advance

GitHub Git-credential prompt

isGitHubAutoAdvancePrompt watches output for "Authenticate Git with your GitHub credentials?" or any line containing both "Press Enter" and "github.com" and queues a \n write back into the PTY. The queue drains as soon as the PTY exists, so output that arrives before the child is wired up still triggers an advance.

10-minute PTY budget

Regular commands get a 120s ceiling. Interactive connects multiply that by 5 (COMMAND_TIMEOUT_MS * 5 = 600s) so a user has room to copy a device code, open a browser, authenticate, and come back without the PTY being killed out from under them.

7d · HTTP surface & operation manager

The HTTP surface lives at /capabilities and is mounted in runtime.ts alongside the agent's HTTP service. Two shapes of endpoint: synchronous reads that return the current capability snapshot, and asynchronous writes that return a 202 Accepted with an operation id you then poll. Async is used wherever the work could take seconds (npm install) or minutes (interactive login).

Method Path Returns Notes
GET /capabilities { capabilities } Refreshes every tool's status before responding.
POST /capabilities/tools/{id}/install 202 { operation } Background; npm install + symlink. Poll the operation for progress.
POST /capabilities/tools/{id}/update 202 { operation } Alias of install — same code path, same operation type.
POST /capabilities/tools/{id}/connect 200 or 202 { operation } 202 when connect.interactive === "tty"; 200 otherwise (synchronous).
POST /capabilities/tools/{id}/disconnect 200 { capabilities } Always synchronous — logout commands are quick.
POST /capabilities/tools/{id}/refresh-status 200 { capabilities } Re-runs version + status probes for a single tool.
GET /capabilities/operations/{id} { operation } Snapshot: status, accumulated messages, final capabilities or error.
POST /capabilities/operations/{id} { operation } Same body as /input: writes a line into the interactive PTY.
POST /capabilities/operations/{id}/input { operation } Explicit input route; requires status === "waiting_for_input".
DELETE /capabilities/operations/{id} { operation } Cancel a running or waiting operation; kills the PTY if applicable.

CapabilitiesOperationManager in operation-manager.ts is a tiny in-memory registry. Each record carries the operation type (installTool / updateTool / connectTool), the target id, a status (running / waiting_for_input / completed / failed / cancelled), an append-only array of progress messages, and either a final capabilities snapshot or a structured error. Interactive connects additionally keep a handle to the InteractiveCapabilityCommand so input writes and cancellation can reach the PTY.

Pruning runs on every read: completed/failed/cancelled records that haven't been touched in 10 minutes are deleted, and the total record count is capped at 100 by evicting the oldest non-running entries. Active operations are never pruned — a login that takes 20 minutes will still be there.

Helper-mode escape hatch

When ANK1015_CAPABILITIES_HELPER_MODE=1, the service skips the helper dispatch path entirely — this is the env var the helper sets for itself when it recursively invokes the service, so the helper doesn't end up calling the helper. Otherwise, when /opt/ank1015/agent-capabilities-helper is executable, every install-tool, update-tool, install-skill, and set-skill-active goes through it under sudo. The cloud image uses this to run installs with elevated privileges without making the long-running server itself a root process.

The tunnel

In cloud mode the machine server doesn't listen on a public port. The web UI talks to it through the cloud gateway, and the gateway needs a way to reach a server that lives on a private network behind NAT. The tunnel solves that: at startup the server dials out over a single WebSocket to wss://{cloudServer}/machines/tunnel, authenticates with a machine token, and from then on the cloud uses that connection to multiplex every UI request back down to the local 127.0.0.1:{port}.

The whole tunnel lives in one file — tunnel/client.ts — and is wired up at the very end of index.ts. It only starts when all three env vars are present (CLOUD_SERVER_PUBLIC_URL, ANK1015_COMPUTER_ID, ANK1015_MACHINE_TOKEN_FILE); local development runs without them and so without a tunnel.

One outbound WebSocket from the cloud VM to the gateway carries every UI request back to 127.0.0.1:{port}, multiplexed by connectionId.

8a · Connection lifecycle

startMachineTunnelClient() creates a MachineTunnelClient and calls start(), which schedules an immediate connect attempt. Every attempt re-reads the token file from disk — this is what makes token rotation transparent. If the file is missing or empty, the attempt is treated as a failure and a reconnect is scheduled.

The connection itself is a single WebSocket to wss://{cloudServerPublicUrl}/machines/tunnel with an Authorization: Bearer {token} header. On close, every local connection currently bridged through the tunnel is closed with code 1011 and reason "Cloud tunnel closed", the cloud socket is cleared, and a reconnect is scheduled after reconnectMs (default 5000ms). On error, close() is called and the same close handler runs.

start conditions

Three env vars, all required

CLOUD_SERVER_PUBLIC_URL + ANK1015_COMPUTER_ID + ANK1015_MACHINE_TOKEN_FILE. Missing any one of them and the tunnel never starts; local development relies on this to stay purely local.

env cloud-only
token file

Re-read on every reconnect

The token isn't cached in memory. Each reconnect calls readFile(tokenFile, "utf8") and uses whatever is on disk. The cloud supervisor can rotate the token without restarting the server — the next reconnect picks it up.

readFile rotation-safe
reconnect cadence

5s fixed, no backoff

A single guard variable reconnectTimer prevents stacking timers. On disconnect the loop simply schedules connectSoon(5000) again — no exponential backoff, since the gateway is expected to be available and the cost of a 5s gap is bounded.

setTimeout 5000ms
close cleanup

Hang up every bridged session

closeLocalConnections(1011, "Cloud tunnel closed") walks every local WS the tunnel had opened and closes it. From the local server's perspective each of these looks like a normal client disconnect — filesystem watchers tear down, browser-control attaches drop, etc.

code 1011 cascade

8b · WebSocket relay

All tunnel frames are JSON messages tagged by type and a connectionId. A single tunnel WS carries many independent connections, each modelling a UI-to-server channel. The protocol is symmetric: messages flowing cloud→tunnel are CloudTunnelMessage, tunnel→cloud are MachineTunnelMessage.

CLOUD → TUNNEL
open begin a WS bridge

Cloud asks the tunnel to dial ws://127.0.0.1:{port}{path} with an optional metadata object (forwarded as x-heysnap-user-id / x-heysnap-access-session-id / x-heysnap-computer-id headers on the local WS). Tunnel replies with openResult — { ok: true } on local open, { ok: false, error } if the local WS errors before opening.

data message in either direction

Carries a base64 data string and a dataType of "text" or "binary". While the local WS hasn't finished opening, frames queue in pendingData and are flushed once open fires. After open they're decoded and forwarded immediately.

close tear down the bridge

Closes the local WS with the (normalized) code and reason, removes the connection record, and — if it was instead an HTTP request — aborts the in-flight fetch() via its AbortController.

httpRequest one-shot HTTP relay

Cloud sends method, path, headers, optional base64 body, and a stream flag. The tunnel performs a fetch() to http://127.0.0.1:{port}{path} and either buffers the whole response (httpResponse) or streams it as httpResponseStart → httpResponseChunk* → httpResponseEnd.

TUNNEL → CLOUD
openResult handshake outcome

Sent exactly once per open request. ok: true on the local WS's open event; ok: false with error if the local WS errors before opening. The cloud uses this to fail the UI's WS upgrade early instead of waiting for a timeout.

data / close mirror of the local WS

Every byte the local server sends becomes a data frame (rawDataToTunnelPayload classifies it as text or binary and base64s it). The local WS's close event becomes a close frame whose code is run through normalizeWebSocketCloseCode — only 1000, 1001–1014 minus 1004/1005/1006, and the 3000–4999 application range survive; everything else is coerced to 1000.

8c · HTTP & SSE relay

WebSocket bridging covers the filesystem, browser-control, and file-preview channels. Everything else — the agent's REST endpoints, the agent SSE stream, capability calls — comes through as an httpRequest frame. The tunnel decides between two response modes based on the stream flag.

1

register AbortController

→ httpAbortControllers.set(id, ctrl)

Stored by connectionId. A subsequent close frame from the cloud aborts the in-flight fetch() — this is how the UI's abort gets propagated all the way to the local Node fetch, including for long-running SSE streams.

2

fetch local with passthrough

→ http://127.0.0.1:{port}{path}

Method, headers, and optional base64 body are forwarded verbatim. The local server sees a normal Node http request — the tunnel is invisible at this layer.

3a

buffered: stream=false

→ httpResponse with bodyBase64

await response.arrayBuffer(), then send a single httpResponse with status, headers (flattened with Object.fromEntries(response.headers)), and the base64 body. Used for JSON REST endpoints.

3b

streamed: stream=true

→ httpResponseStart / Chunk / End

Send httpResponseStart with status + headers, then iterate the response body via getReader() and emit httpResponseChunk frames (base64 per chunk) until EOF, then httpResponseEnd. This is what carries the agent SSE stream.

4

finally: drop AbortController

→ httpAbortControllers.delete(id)

On success, error, or abort. Errors are translated into a 502 httpResponse with the error message as the body, so the UI sees a proper failure instead of a hanging request.

Metadata headers and authorization boundary

The cloud gateway is the only thing that authenticates the user. Once a request crosses into the tunnel, identity is communicated as opaque header values (x-heysnap-user-id, x-heysnap-access-session-id, x-heysnap-computer-id) on the local WS/HTTP request. The local server trusts these headers because the only way they arrive is via a tunnel that has already presented a valid machine-token Bearer to the gateway. There is no second layer of auth between the tunnel and 127.0.0.1.

Status, restarts & sessions

The server exposes two health endpoints with very different jobs. /health is a liveness check; /status is what the cloud supervisor reads to decide whether it can safely replace the server with a newer build. The decision boils down to one boolean — safeToRestart — which in turn is a literal sum across four independent session counters.

This section walks through the two endpoints, the four counters that feed them, and how the cloud release pipeline uses them to ship without dropping in-flight work.

9a · /health vs /status

Endpoint Body Who calls it Failure means
GET /health { ok: true } Process supervisor liveness probes, the cloud VM's healthcheck. The Node process isn't accepting HTTP — restart immediately.
GET /status MachineServerStatus The release controller; UIs that show "1 agent run in flight". Same as /health, but with shape: it's an aliveness and business-state probe.

/health is cheap and answers "is the process up?" — nothing else. Anything that can keep an HTTP listener serving will pass it, including a server whose agent harness has crashed. That's deliberate: the supervisor uses it to decide whether to restart, and a richer probe would create a feedback loop where a degraded server gets killed before /status can describe what's degraded.

/status returns a structured snapshot every time it's hit. There's no caching, no debounce — the counters are O(1) reads from the underlying WebSocketServer client sets and the agent run manager's internal map, so the cost is negligible.

MachineServerStatus shape

{ ok: true, version, activeSessions: { filesystem, filesystemPreview, browserControl, agent, total }, safeToRestart }. version comes from options.version → MACHINE_SERVER_VERSION env → the literal string "development", in that order.

9b · The four session counters

Every counter is read directly off the data structure that already exists for the feature. There's no separate bookkeeping — if a counter is wrong, it's because the underlying subsystem leaked a session, not because the status code drifted from the truth.

filesystem

filesystemSocketServer.clients.size

The raw ws.WebSocketServer client set. Each open /filesystem WebSocket counts as 1, regardless of how many open files or subscriptions it tracks. Drops to 0 the instant the last UI tab closes its tunnel.

ws.clients per-socket
filesystemPreview

filesystemPreviewSocketServer.clients.size

Same shape but for the previewer's WS path. The HTTP preview surface doesn't contribute — only the live WebSocketServer attached via bindPreviewWebSocketServer.

ws.clients previewer
browserControl

browserControlService.socketServer.clients.size

The number of Chrome extension instances currently dialled in to the broker. Note that this counts the extension side — the agent posting commands over HTTP isn't a session here. If no extension is attached the counter is 0 even when the agent is mid-call.

ws.clients extension only
agent

runManager.getActiveRunCount()

Calls pruneCompletedRuns() first, then counts records whose status isn't completed or failed. So running, queued, and cancelling all keep the count above zero; terminated runs drop out immediately, with stale records evicted by the 10-minute TTL.

runsByInternalId + TTL prune

total is simply the sum of the four. There is no weighting — one filesystem WS counts the same as one in-flight agent run. The point isn't to estimate load; it's to detect zero.

9c · safeToRestart & the supervisor

safeToRestart is the literal expression total === 0. It says "no UI client is currently subscribed and no agent run is in flight," which is the same as "killing the process now will not cancel anyone's work."

The cloud release controller polls /status, waits for safeToRestart: true, and only then asks the supervisor to swap in the new container. While work is in flight, deploys queue. The version field is what the controller compares against the target build to know whether a swap is needed at all.

1

release controller publishes a target version

→ MACHINE_SERVER_VERSION

A new tag becomes the cloud VM's desired version. The controller knows the currently-running version because it reads /status.

2

poll until safeToRestart === true

→ GET /status

As long as a UI is open, an SSE stream is running, or the extension is attached, total > 0 and the controller waits. Idle servers report safeToRestart: true within seconds of the last client closing its WebSocket.

3

SIGTERM → graceful stop()

→ runtime.ts::stop()

index.ts registers SIGINT / SIGTERM handlers that call runningServer.stop(). stop() closes the three WebSocket servers in parallel, then closes the HTTP server, then exits. Any tunnel currently bridged through will see a normal close on its local sockets.

4

supervisor brings the new container up

→ tunnel reconnect cycle

Boot, capability adoption, codex config write, and tunnel dial-out all happen in the new process. From the UI's perspective there's a sub-second gap where the cloud gateway reports the machine as offline, then everything resumes — identical port, identical paths.

What doesn't persist across restarts

Completed agent run records (purely in-memory), capability operation logs (also in-memory, 10-min TTL), filesystem viewState for connected UIs, browser- control attachment scratch files in /tmp, and the cached Last-Event-ID on the gateway side. What does persist: state.json for capabilities, installed npm tool packages under toolsRoot, bundled skill folders in skillsCatalogDir, the user's ~/.codex/config.toml, and the filesystem root itself.

Edge cases & gotchas

A closing pass over the things that aren't obvious from reading any single file — behaviours that surprise people, invariants that hold only because of how two subsystems happen to agree, and choices that look arbitrary until you've debugged the case they were made for. Skim before changing anything load-bearing.

10a · Filesystem

isSafeSymlink

Sandbox holds on followed links

ensureWithinRoot rejects relative escapes (.., absolute paths, null bytes, backslashes) before the call ever reaches the filesystem. The second guard is isSafeSymlink: if an entry is a symlink, its realpath is re-resolved and re-checked. A symlink that points outside the root is silently skipped from listings rather than throwing — broken links don't crash the UI.

sandbox two-layer check
100ms debounce

One watcher, one debounce timer per session

Chokidar fires per inode change; an editor saving a file can produce 3–5 events in quick succession. The 100ms debounce collapses these into one snapshot push. Side effect: the UI sees changes 100ms after the disk does, which is invisible to a human but matters when chaining a watcher fire to another watcher in tests.

chokidar debounce
setOpenFiles

Open files are tracked, not watched

setOpenFiles stores the UI's open-file list on shared viewState (deduped, normalised, sorted) and acks. The server does not attach a separate watcher for those paths — clients learn about content changes through the directory snapshot stream that the active-directory watcher already drives. The list is purely metadata: it survives across reconnects within the process via viewState restore.

viewState no-extra-watcher
upload flag: "wx"

Uploads refuse to overwrite

uploadFiles opens with flag: "wx" so an existing path fails the write rather than silently replacing the file. The UI is expected to rename or confirm overwrite first. Mtime is preserved from the upload payload, not taken from the moment of write — "show me when the user created this file," not "when did we receive it."

no-clobber mtime preserve

10b · Agent

clientRunId

Idempotency on POST /agent/runs

A retried POST with the same clientRunId returns the existing run's identifiers instead of starting a second run. This is what makes the UI safe to retry on flaky networks — the same body, posted twice, is one logical operation.

dedupe key 3 maps
Last-Event-ID replay

SSE reconnect is snapshot + diff, not stored log

The run manager doesn't keep every emitted SSE envelope. On reconnect with Last-Event-ID it reconstructs a current thread snapshot and diffs it against where the client said it was. Side effect: a client that disconnects, idles for >10 minutes, then reconnects may find the run TTL-evicted — the replayAfterEventId path returns the snapshot-only form.

SSE 10-min TTL
x-accel-buffering: no

SSE survives the tunnel

The agent's SSE handler explicitly sets x-accel-buffering: no. The tunnel's httpRequest with stream: true respects this by reading response.body chunk-by-chunk; without the header an intermediary could buffer the whole response and break live event delivery.

SSE header tunnel stream
codex stderr ring

Last 20 chunks, surfaced on crash

CodexStdioAppServerClient keeps the last 20 stderr chunks in a bounded buffer. If the subprocess exits unexpectedly, the buffer becomes the body of the resulting AgentRunEvent with type error. Without this the UI would just see "codex crashed" with no context.

crash forensics ring buffer

10c · Capabilities

helper recursion guard

ANK1015_CAPABILITIES_HELPER_MODE=1

The capabilities service prefers to delegate installs to /opt/ank1015/agent-capabilities-helper when present. The helper sets ANK1015_CAPABILITIES_HELPER_MODE=1 in its own environment so that when it shells back into the service, the service skips the helper path and does the work directly. Without this, the helper would call itself in a loop.

sudo helper recursion guard
paths fallback

Cloud layout silently degrades to user layout

If cloud-style paths fail with EACCES/EPERM and no path was explicitly overridden, initialize() retries under $HOME/.ank1015. This is what lets local development run on a laptop without ever being root, but it also means a misconfigured cloud VM can silently land in the wrong place — check state.updatedAt path if debugging.

EACCES retry silent
symlinked active skills

Catalog is copied, activation is a symlink

writeSkillCatalog does an atomic cp -r + rename into skillsCatalogDir. setSkillActiveOnDisk creates a symlink from activeSkillsDir/{id} into the catalog dir. Toggle is a single rm + symlink; no file copying after install.

cp + rename symlink toggle
state.json atomic write

Temp file + rename, every save

saveState() writes to {stateFile}.{uuid}.tmp then renames over the target. A crash mid-write can leave a stray .tmp but cannot corrupt the live file. The state is reloaded by reading the file fresh after every helper-mediated operation — the helper writes, the service re-reads.

atomic crash-safe

10d · Tunnel & browser control

close code coercion

1004 / 1005 / 1006 → 1000

normalizeWebSocketCloseCode strips the reserved-by-spec close codes (1004, 1005, 1006) and anything outside the valid ranges, replacing them with 1000. Without this, a local close with 1006 (abnormal closure) would cause the tunnel to send an invalid frame and the cloud WS to drop with a protocol error.

WS spec protocol-safe
pendingData queue

Frames before local WS open are buffered

A cloud-originated data frame can arrive while the local WS is still handshaking. The tunnel queues these in pendingData and flushes them once open fires. Without this, the first message of any session would race the local WS handshake and frequently be lost.

race fix in-order
trust boundary

x-heysnap-* headers are unauthenticated locally

The local server reads x-heysnap-user-id et al. as ground truth. These are only trustworthy because the only path onto 127.0.0.1 is via a tunnel that has already presented a valid machine-token Bearer to the gateway. If you ever expose the server on a non-loopback interface, this assumption breaks.

loopback only gateway-auth
attachment pull / output push

Asymmetric chunk model

Browser-control attachments are pulled by the extension in 512KB chunks when it's ready — the server holds the file open and serves slices. Browser- control outputs are pushed by the extension at sequential byte offsets, with the server writing each chunk to a temp file and atomically renaming on completion. Different directions, different concerns, different code paths.

pull vs push 512KB / atomic

10e · Miscellaneous

DSR auto-reply

Fake cursor-position for headless PTY

Some CLIs (vercel, supabase) emit ESC[6n expecting a real terminal to reply with the cursor position. The service writes back ESC[1;1R on the PTY so the child doesn't block. Without it the login prompts hang silently.

VT100 PTY
gh auto-advance

Press-Enter prompts pre-queued

gh auth login has a "Press Enter to authenticate with your GitHub credentials?" prompt that has no value to round-trip to the user. The service pattern-matches it on the PTY output and queues a \n write, even if the match arrives before the PTY handle is ready (the queue drains on attach).

pattern prequeue
toolsBinDir on PATH

npm-installed wins over host installs

commandEnv() prefixes PATH with {toolsRoot}/bin. So if the user has a stale vercel on their system PATH, the npm-pinned version installed by the service still wins inside every spawned child. Outside spawned children — e.g. in the agent harness when it later calls codex — the cached codexBin path is used instead, so the same precedence holds.

PATH version-pinned
in-memory-only state

Restart drops live sessions, never persisted state

Run records, capability operation logs, browser-control attachment scratch, file- preview WS clients, and the agent's SSE buffer all live in process memory and are gone after a restart. Only state.json, installed tool packages, bundled skill folders, the filesystem root, and the persisted Codex config survive.

memory only persists: disk
If you remember one thing from this doc

The machine server is the same code running in different environments. Cloud vs local development is decided by environment variables, not by branches in the source. Most of the subtlety in the codebase — the path fallback, the trust boundary, the tunnel, the safeToRestart counter — exists to keep both deployments correct without forcing either one to know about the other.
