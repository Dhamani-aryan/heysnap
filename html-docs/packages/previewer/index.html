Overview

What it is, and why it exists

The previewer is the single place HeySnap renders files. PDFs, DOCX, PPTX, XLSX, Markdown, source code, images, video, audio, and live HTML all flow through the same surface, with one consistent dark theme and one live-reload model. The user never sees a different viewer chrome depending on what they opened.

It is intentionally decoupled from packages/server. Mounting the previewer requires only an HTTP host and a path resolver, which is why the dev playground, the machine-server, and the mobile shell can all embed the same viewer code without owning any of its internals. The package exports two entry points — startPreviewServer for a turnkey listener, or createPreviewService when the caller already has its own HTTP and WebSocket plumbing.

On the wire the model is small: the browser asks the server to watch a path, and the server pushes a typed message every time that path changes on disk. The client picks a viewer based on the message, and that’s the whole loop.

live

File changes stream in

A chokidar watcher on the server pushes updates over WebSocket with a 20 ms debounce. No polling, no manual refresh.

sandboxed

Every path resolved against a root

Requests are normalized and checked with ensurePathInside before any file is touched. Absolute paths are rejected unless explicitly allowed.

pluggable

Bring your own resolver or converter

Swap the path resolver, the XLSX converter, or the entire HTTP host. The viewer code and protocol stay the same.

The big picture

The package splits into three layers. At the top is the client — a React SPA bundled into a dist directory that any HTTP host can serve. At the bottom is the server — a small Node module that answers HTTP requests, runs a WebSocket endpoint, and watches files. In the middle, a single TypeScript file defines every message that crosses the wire. Two halves, one contract.

Anatomy of one preview

A single preview is six stages long. The browser parses its query string, opens a WebSocket, sends one watch message, and waits. The server resolves the path inside a sandbox, branches by file type, and pushes a typed message back. The client picks a viewer, renders, and then the loop runs forever — every time the file mutates on disk a new message arrives and the viewer re-keys.

The swim-lane below shows what crosses the wire at each stage. The cards beneath expand each stage with the file that owns it.

  1. 1

    Connect

    socket open

    App.tsx reads ?path, ?root, and ?chrome from the URL and calls new WebSocket(<basePath>/ws). The server’s HTTP upgrade handler routes that path to WebSocketServer.handleUpgrade, which fires connection and triggers service.handleWebSocketConnection — a fresh PreviewSocketSession is created with its own connectionId.

    src/client/App.tsx · src/server/index.ts · src/server/service.ts
  2. 2

    Watch

    client → server

    On open, the client sends a single {type:"watch", path, root?, publicBasePath} message. parseClientMessage validates JSON and required fields, rejects on a missing path, and normalizes the optional publicBasePath so subsequent asset URLs use the right prefix.

    src/client/App.tsx · src/server/service.ts
  3. 3

    Resolve & sandbox

    server only

    createDefaultPreviewPathResolver trims the path, rejects null bytes, resolves it against the configured rootPath, and runs ensurePathInside — the single check that blocks .. escapes. Absolute paths are rejected here unless allowAbsolutePaths is on. The same check runs again for an optional HTML root.

    src/server/paths.ts
  4. 4

    Branch by extension

    server only

    sendUpdate inspects the extension and picks one of three paths. .xlsx spawns the heysnap-xlsxl CLI, reads workbook.json, and rewrites every image’s assetPath into a URL that lands on /api/xlsx-assets/<connId>/…. .html/.htm registers an HTML root and builds an iframe URL into /api/html-preview/<connId>/…. Everything else is read once and base64-encoded inline.

    src/server/service.ts · src/server/xlsx.ts · src/server/mime.ts
  5. 5

    First emit & render

    server → client

    The server sends one of file, workbook, or htmlPreview. The client receives, drops the type tag, and stores the rest as a PreviewItem. Previewer.tsx then dispatches by kind — PDF, DOCX, PPTX, XLSX, Markdown, code, image/video/audio, or download fallback.

    src/server/service.ts · src/client/App.tsx · src/client/Previewer.tsx
  6. 6

    Live updates

    repeat until close

    A chokidar watcher attaches to the file (or to the HTML root for HTML previews), ignoring node_modules, .git, dist, and other noisy directories. Each change schedules a 20 ms-debounced timer; on fire, sendUpdate runs again. The client’s buffer reducer queues the new item as pendingSlot; the new viewer paints off-screen and swaps in on onReady, so the cross-fade between versions is flicker-free. On socket close the watcher is destroyed and the connection’s asset directory is removed.

    src/server/service.ts · src/client/Previewer.tsx

The protocol

Two messages flow from client to server. Five flow back. Every message carries a literal type field, so dispatch on either side is a single switch. Adding a new file kind starts here — change protocol.ts and let the type errors lead you to every callsite.

The catalog below is the entire wire vocabulary. The client never sees an untyped payload, and the server never accepts one.

Client → Server · 2 messages
watch App.tsx → PreviewSocketSession

Sent once on socket open after the client reads ?path from the URL. Re-sent if ?path or ?root change — the socket is torn down and a new one opens. Missing path is rejected with an error.

Schema 
{
  type: "watch";
  path: string;
  root?: string;
  publicBasePath?: string;
}
Example 
{
  "type": "watch",
  "path": "docs/report.pdf",
  "root": "/Users/me/work",
  "publicBasePath": "/preview"
}
ping liveness probe

Optional. A host or test harness can send this to confirm the socket is alive; the server replies with a matching pong carrying the same requestId and an ISO server timestamp.

Schema 
{
  type: "ping";
  requestId?: string;
}
Example 
{
  "type": "ping",
  "requestId": "8c3e-1"
}
Server → Client · 5 messages
file inline bytes · non-xlsx, non-html

Emitted for every file kind that isn’t a workbook or live HTML. Bytes are read once and base64-encoded into data. The MIME is computed by mimeForPath.

Emitted for .xlsx paths. createWorkbookPreview spawns the heysnap-xlsxl CLI, reads its workbook.json, strips chart asset fields, and rewrites every image assetPath into an assetUrl that lands on /api/xlsx-assets/<connId>/…. The original .xlsx bytes also ride along as base64 in data so the viewer can expose a download.

  name: string;
  size: number;
  mtime: number;
  data: string;       // base64 .xlsx

}

htmlPreview .html / .htm · iframe URL

Emitted for .html and .htm. The server registers the HTML root for this connection and returns a URL into /api/html-preview/<connId>/…; the client mounts it in an <iframe> keyed on path:mtime.

}
error terminal for the current watch

Anything that goes wrong becomes a string. Common triggers: bad JSON, missing path, path outside the sandbox, stat says it’s a directory, the watcher errors, or the file gets unlinked mid-watch.

Schema 
{
  type: "error";
  message: string;
}
Example

Echoes the requestId from the original ping and stamps the server’s current ISO time so a host can compute round-trip latency.

{
  type: "pong";
  requestId?: string;

Client-side derivation
PreviewItem App.tsx state shape

The client drops the type tag and reshapes the successful messages into a single discriminated union keyed by kind. Previewer.tsx switches on kind first, then on MIME and extension for the generic file branch.

Type 
type PreviewItem =
  | { kind: "file";     file: PreviewFile }
  | { kind: "workbook"; data: PreviewWorkbook }
  | { kind: "html";     data: PreviewHtml };
Mapping 
file        → { kind: "file", file }
workbook    → { kind: "workbook", data }
htmlPreview → { kind: "html", data }
error       → setError(message)
pong        → (ignored by viewer)

The server, file by file

Six files do all the server work. service.ts is the hub: it owns routing and the per-connection state machine, and it pulls in the three leaves (paths.ts, mime.ts, xlsx.ts) plus the shared protocol.ts types. index.ts wraps the service in a real HTTP + WebSocket listener. dev-server.ts is an alternative entry that swaps the real listener for Vite middleware.

src/server/index.ts

HTTP + WebSocket host · the turnkey entry

Wraps service.ts in a real Node listener. Creates an http.Server that forwards every request to service.handleRequest, and a WebSocketServer({ noServer: true }) that takes the upgrade event and binds the socket to a new PreviewSocketSession via bindPreviewWebSocketServer.

Returns a RunningPreviewServer handle with the bound URL, the base path, the websocket path, and a stop() that closes both servers cleanly. Also re-exports the path utilities and the protocol types so hosts only need to import this one module.

src/server/service.ts

PreviewService + PreviewSocketSession · the core

Two classes do everything. PreviewService is stateless across requests: it routes /api/health, /api/html-preview/*, /api/xlsx-assets/*, and the SPA shell; injects the publicBasePath into index.html; and builds asset URLs that consumers can fetch later. It also keeps two connection-keyed maps: htmlRoots and xlsxAssetDirs.

PreviewSocketSession is per-connection. It parses every incoming message, calls resolveWatchPath, tears down any prior watcher via replaceWatch, fires sendUpdate immediately, and starts a chokidar watcher with a 20 ms debounce. Each subsequent change re-enters sendUpdate, which branches by extension into sendBytes, sendHtmlPreview, or sendWorkbook (the workbook branch reads the raw bytes alongside the parsed JSON so the viewer can expose a download).

src/server/paths.ts

The security boundary

Small file, load-bearing. createDefaultPreviewPathResolver normalizes the incoming path, rejects empty strings and null bytes, and — unless allowAbsolutePaths is set — resolves it against the configured rootPath. The actual sandbox check is ensurePathInside: a one-liner that compares the resolved absolute path against the root and throws a PreviewPathError if it escapes.

Also owns the URL-side helpers normalizeBasePath (ensures leading slash, no trailing slash) and stripBasePath (subtracts the base from an incoming request URL).

The client, file by file

Four files plus the components/ directory cover the entire browser side. main.tsx is a one-screen React bootstrap. App.tsx owns the WebSocket lifecycle, the URL contract, and a double-buffered render machine. Previewer.tsx is a pure router: given a PreviewItem and a theme, it picks one of nine concrete viewers from components/viewers. styles.css carries the dark and light theme tokens.

src/client/App.tsx

URL → WebSocket → double-buffered render

usePreviewQuery reads ?path, ?root, ?chrome, and ?theme (dark default, light opt-in) from window.location.search. With no path, the component renders PreviewPlayground — a tiny form that just updates the URL.

The main useEffect opens new WebSocket(buildPreviewWebSocketUrl()), drives a four-state machine (idle · connecting · open · closed), and on open sends one watch message carrying the path, optional root, and the publicBasePath read from the injected window.__HEYSNAP_PREVIEWER_BASE_PATH__.

Incoming messages are routed through handlePreviewMessage into a useReducer-driven PreviewBufferState. The reducer keeps two slots — visibleSlot and pendingSlot — so a new file mounts off-screen and only swaps in once it fires its onReady callback. The result is a flicker-free cross-fade between previews instead of a tear-down / remount blink.

src/client/Previewer.tsx

The viewer router

Pure dispatch. Takes an item plus a theme: "dark" | "light" prop and an onReady / onError pair that the app’s buffer uses to know when a viewer has painted. A local VIEWER_THEMES table turns the theme name into the concrete header / body / sidebar colors and the Monaco theme id used by the code and markdown viewers.

The top-level switch is on item.kind: workbook renders HeySnapXlsxViewer with the parsed JSON and a download blob built from the base64 data; html renders HeySnapHtmlViewer with the server-built URL (v=<mtime> appended to bust the cache); file falls into renderFile().

renderFile() walks an if-ladder in this order: PDF, DOCX, PPTX, Markdown, code, then image/, video/, and audio/ by MIME prefix. Each branch decodes the base64 via a useMemo’d base64ToBytes and feeds the matching local viewer with theme props. Anything that doesn’t match lands in FallbackPreview: text/ · json · xml get a <pre>, everything else gets a download link.

Every viewer is keyed on ${file.path}:${file.mtime}, but the actual remount blink is hidden by the buffer in App.tsx — the new viewer paints into the pending pane and swaps in once ready.

Integration & operation

Two entry points cover almost every host. Pick startPreviewServer for a turnkey HTTP + WebSocket listener you can bind a port to. Pick createPreviewService when you already own the HTTP host — mount its request handler under any base path and bind its WebSocket server to your existing upgrade event.

The same PreviewServiceOptions drive both. The tables below name every knob, and the proxy notes at the bottom cover the one piece of configuration that’s easy to miss.

Two ways to host

Pick the turnkey listener, or embed the service in your own server.

Turnkey

startPreviewServer

One call. Binds an http.Server + a WebSocketServer, hooks them together, and returns a handle with url, basePath, websocketPath, and stop(). 

import { startPreviewServer } from "@ank1015-app/previewer";

const preview = await startPreviewServer({
  rootPath: "/workspaces/project",
  port: 4719,
});

console.log(preview.url);
// => http://127.0.0.1:4719/preview

// later
await preview.stop();
Embedded

createPreviewService

Bring your own http.Server and WebSocketServer. Forward HTTP traffic under service.basePath to service.handleRequest; route the upgrade event for service.websocketPath to your WS server. 

import { createServer } from "node:http";
import { WebSocketServer } from "ws";
import {
  createPreviewService,
  bindPreviewWebSocketServer,
} from "@ank1015-app/previewer";

const service = createPreviewService({
  rootPath: process.cwd(),
  basePath: "/preview",
});

const wss = new WebSocketServer({ noServer: true });
bindPreviewWebSocketServer(wss, service);

const server = createServer((req, res) => {
  void service.handleRequest(req, res);
});

server.on("upgrade", (req, socket, head) => {
  const url = new URL(req.url ?? "/", "http://x");
  if (url.pathname !== service.websocketPath) {
    socket.destroy();
    return;
  }
  wss.handleUpgrade(req, socket, head, (ws) =>
    wss.emit("connection", ws, req)
  );
});

server.listen(4719);

Mounting behind a proxy

How the previewer learns its public URL when something else owns the front door.

Two equivalent signals

The client sends publicBasePath in the watch message; the proxy can additionally forward the x-heysnap-preview-public-base-path HTTP header. Whichever the server sees first wins. If neither is set the server falls back to its internal basePath, which is fine when the previewer is exposed directly.

Edge cases & gotchas

Small details that change behavior in ways that aren’t obvious from the type signatures. Each card names the file and the rule, in case you ever need to re-find it in source.

Routing

HTML wins over “HTML as code”

A .html or .htm file becomes an htmlPreview message and renders in an iframe. The server’s extension check (isHtmlPath in service.ts) runs before the generic file branch, so the code viewer never sees it — even though .html is in the client’s CODE_EXTENSIONS set.

Workbooks

Charts are stripped from workbooks

stripWorkbookChartAssets in xlsx.ts walks every sheet and deletes assetPath, assetUrl, renderedAssetPath, and renderedAssetUrl from chart objects before sending. Images survive with rewritten assetUrls; charts will not render.

Lifecycle

File removed is not a new state

When chokidar fires unlink, the session sends an error message ("File removed: <publicPath>") rather than a new item kind. The viewer stays mounted; only the error banner appears.

Watcher

Noisy directories are always ignored

The chokidar ignored regex in replaceWatch skips node_modules, .git, dist, build, .next, .cache, .turbo, and .parcel-cache. Even inside an HTML root, changes under those paths will not trigger an update.

Cleanup

Asset URLs die with the socket

cleanupConnection deletes the connection’s xlsx asset directory and forgets the HTML root when the socket closes. Bookmarking an /api/html-preview/<connId>/… or /api/xlsx-assets/<connId>/… URL is safe only for the lifetime of the current WebSocket.

Debounce

20 ms is the default coalesce window

Editors that save in two passes (write temp + rename) usually settle inside that window. For chattier writers or slow disks, bump debounceMs. Chokidar already applies awaitWriteFinish with a 30 ms stability threshold on top of this.

Sandbox

Absolute paths are rejected by default

createDefaultPreviewPathResolver requires rootPath to be set when paths are relative, and rejects absolute paths unless allowAbsolutePaths is on. Symbolic links aren’t followed across the sandbox boundary — ensurePathInside compares resolved absolute paths, not lexical ones.

Reconnect

Path changes tear down the socket

On the client, changing ?path or ?root doesn’t reuse the current socket — the effect closes the existing connection and opens a new one. Connection-id-scoped asset URLs from the old socket are immediately stale.

Re-render

Remounts are hidden by the double buffer

Previewer.tsx keys every viewer on ${path}:${mtime}, so each update remounts the component and discards its internal state. App.tsx hides that blink: the new viewer paints into a pending pane and only swaps in when it fires onReady. Stateful viewers still lose their state across reloads and must persist externally if needed.

Bytes

Workbooks ride bytes too

Plain files are read fully into memory and base64-encoded into the file message. Workbooks now do the same on top of the parsed JSON so the viewer can offer a download — very large .xlsx files pay double. For huge binaries, swap in a custom resolvePath + handler pair that streams instead.
